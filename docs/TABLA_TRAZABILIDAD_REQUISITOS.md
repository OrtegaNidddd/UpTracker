## 1. Introducción y Metodología de Trazabilidad

El presente documento establece la **Matriz de Trazabilidad de Requisitos de Software** para la plataforma **UpTracker**, contrastando formalmente los requisitos funcionales extraídos del documento del Proyecto Pedagógico de Aula (`docs/PPA_UpTracker.md`) frente a los artefactos de código fuente construidos en el repositorio (`routes/`, `app/`, `database/`, `resources/` y `tests/`).

La trazabilidad bidireccional garantiza que cada funcionalidad descrita en la propuesta académica cuente con su correspondiente implementación en backend (rutas, controladores, modelos, migraciones, jobs y servicios), interfaz de usuario en frontend (vistas Blade, componentes Alpine.js, gráficos Chart.js) y cobertura de pruebas automatizadas en PHPUnit.

## 3. Desglose Detallado por Componentes y Archivos del Sistema

### 3.1. Rutas del Sistema
* [`routes/web.php`](file:///C:/Users/nelly/UpTracker/routes/web.php): Centraliza las rutas de la aplicación web protegidas con middleware `auth` y `verified`. Incluye el panel `/dashboard`, el ABM de `/services`, el módulo de `/notification-channels`, la prueba de canales en tiempo real (`/test`), la página de estado pública en `/status`, el endpoint JSON `/status/public` y el generador de `sitemap.xml`.
* [`routes/api.php`](file:///C:/Users/nelly/UpTracker/routes/api.php): Provee la API RESTful bajo tokens de Sanctum con rate limiting por niveles: `throttle:api.auth` (10 req/min para login/registro), `throttle:api` (60 req/min para CRUD de servicios y canales) y `throttle:api.public` (30 req/min para la página de estado pública).
* [`routes/console.php`](file:///C:/Users/nelly/UpTracker/routes/console.php): Registra el Scheduler de Laravel para despachar el job `CheckEndpointStatus` respetando intervalos sub-minuto (cada 10s, 30s, 60s, etc.) con prevención de solapamiento (`withoutOverlapping`), y programa la purga diaria `monitor:prune`.

### 3.2. Controladores y Lógica de Aplicación
* [`app/Http/Controllers/DashboardController.php`](file:///C:/Users/nelly/UpTracker/app/Http/Controllers/DashboardController.php): Agrega el uptime de 24 horas mediante consultas por lotes sin problema $N+1$, extrae los últimos 50 registros cronológicos de latencia para Chart.js, ejecuta el análisis SLA a 30 días y genera la tendencia histórica de 7 días.
* [`app/Http/Controllers/ServiceController.php`](file:///C:/Users/nelly/UpTracker/app/Http/Controllers/ServiceController.php): Administra la creación, edición, detalle y eliminación de endpoints, permitiendo la configuración de umbrales SLO (Disponibilidad % y Latencia ms) con aislamiento estricto por usuario (`user_id`).
* [`app/Http/Controllers/NotificationChannelWebController.php`](file:///C:/Users/nelly/UpTracker/app/Http/Controllers/NotificationChannelWebController.php): Permite gestionar canales de alerta (Correo, Discord Webhook, Telegram Webhook) y provee el método interactivo `test()` para disparar alertas de prueba en tiempo real.
* [`app/Http/Controllers/Api/PublicStatusController.php`](file:///C:/Users/nelly/UpTracker/app/Http/Controllers/Api/PublicStatusController.php): Endpoint público que consolida el estado global (`Operational`, `Major_Outage`, `Partial_Outage`, `Degraded_Performance`), listas de servicios, incidentes activos/resueltos y métricas agregadas de SLA.
* [`app/Http/Controllers/Api/ServiceApiController.php`](file:///C:/Users/nelly/UpTracker/app/Http/Controllers/Api/ServiceApiController.php): Controlador API para consumo programático con validación de cabeceras personalizadas, métodos HTTP y parámetros SLA.

### 3.3. Procesamiento Asíncrono, Sondeo y Confiabilidad
* [`app/Jobs/CheckEndpointStatus.php`](file:///C:/Users/nelly/UpTracker/app/Jobs/CheckEndpointStatus.php): Trabajo encolado (`ShouldQueue`) que realiza la petición HTTP con timeout de 10s, captura el TTFB mediante TransferStats de Guzzle, audita certificados SSL/TLS para HTTPS, abre o resuelve incidentes dinámicamente, sincroniza el estado de SLA y emite el evento de WebSocket `EndpointStatusUpdated`.
* [`app/Services/SlaService.php`](file:///C:/Users/nelly/UpTracker/app/Services/SlaService.php): Motor matemático que implementa los conceptos SRE: cálculo de SLI de disponibilidad y rendimiento, cálculo de percentil 95 ($P95$), cómputo del Error Budget restante, clasificación tricolor (*Cumple*, *En riesgo*, *Incumple*), persistencia de snapshots diarios y emisión de alertas preventivas.
* [`app/Listeners/DispatchIncidentNotifications.php`](file:///C:/Users/nelly/UpTracker/app/Listeners/DispatchIncidentNotifications.php): Listener encolado (`ShouldQueue`) que envía notificaciones de incidentes a través de correo (Mailable) y webhooks (Discord/Telegram) con reintentos (`tries = 3`) y control de fallos.
* [`app/Console/Commands/BenchmarkEndpointsCommand.php`](file:///C:/Users/nelly/UpTracker/app/Console/Commands/BenchmarkEndpointsCommand.php): Comando Artisan (`monitor:benchmark`) diseñado para someter al sistema a una carga de 30 endpoints simultáneos y evaluar el consumo de CPU en Windows y Linux.

### 3.4. Base de Datos y Modelo Relacional
* **Entidad `users`**: Administra cuentas de usuario y credenciales criptográficas seguras.
* **Entidad `services`**: Almacena URL, intervalo, método HTTP, headers JSON, umbral de latencia, estado SSL y metas de nivel de servicio (`slo_availability_target`, `slo_latency_target_ms`, `sla_status`, `error_budget_percentage`).
* **Entidad `latency_logs`**: Serie temporal de chequeos individuales (`service_id`, `latency_ms`, `http_status_code`, `status`, `checked_at`).
* **Entidad `incidents`**: Registro de períodos de indisponibilidad y degradación (`incident_type`, `started_at`, `resolved_at`, `duration_seconds`, `details`).
* **Entidad `notification_channels`**: Destinos de alertamiento (`type`, `target_destination`, `is_active`).
* **Entidad `sla_histories`**: Snapshots diarios para auditoría histórica de SLA (`snapshot_date`, `total_checks`, `up_checks`, `uptime_sli`, `avg_latency_ms`, `p95_latency_ms`, `error_budget_percentage`, `status`).
